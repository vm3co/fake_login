## 目標與問題

Job item 去重只涵蓋部分手動工作，無法防止清單同步、啟動預熱與排程同時操作相同任務。本票建立資料庫層保護，不能把 UI disabled、process-local lock 或現有工作佇列當作唯一一致性保證。

## 範圍

1. 定義同步的 `prepare`／`apply` 分界：遠端請求在交易外完成，並保存本地預期 generation／revision；交易內才鎖定及寫入。
2. 以原始任務 UUID 取得 PostgreSQL transaction-scoped advisory lock，現行 row 不存在時也必須串行化，避免兩個匯入同時認為自己是新任務。
3. 鎖定現行 row、核對預期本地版本與修訂；每次同步提交遞增修訂，新匯入／重建／人工重匯更換本地 generation。
4. prepared snapshot 過期時不得覆寫；採有限次重新準備或回傳可重試衝突，不能無限重試。
5. 同樣保護「確認不存在」結果，避免較早取得的 404 把另一個工作剛匯入的新版搬走。
6. 定義一致的鎖順序：任務鎖 → 現行任務 row → 待搬明細 rows；備援複製在鎖後讀取，配合 Trigger worker 的明細更新鎖。
7. 使用穩定的 advisory key 產生方式，不能用跨 process 不穩定的 Python `hash()`；鎖自動隨 commit／rollback 釋放。

## 排除事項

- 不實作備援 payload、遠端判斷、版本替換或 UI。
- 不新增分散式鎖服務、不更換佇列架構、不讓網路請求長時間佔用資料庫 row lock。

## 驗收條件

- [x] 同 UUID 的兩個 apply 串行化；不同 UUID 不被單一全域鎖全部擋住。
- [x] 無現行 row 時的兩個匯入不會同時通過「無資料」檢查。
- [x] A 準備完成、B 先提交後，A 的舊 revision 被拒絕。
- [x] 舊 404 不會搬走 B 剛寫入的新版。
- [x] rollback、例外與取消釋放鎖，後續工作仍能執行。
- [x] 回報衝突可供工作層判斷，不被誤當成成功。

## 聚焦驗證

用專用 PostgreSQL 的兩個獨立 session 與可控制執行順序的測試同步點驗證；不能用單一 AsyncMock 代替並發鎖測試。測試不使用任意 sleep 等待來猜順序。

## 交付給下一票

提供鎖定介面、交易擁有者、預期版本結構、衝突例外／狀態與鎖順序，供原子搬移及同步核心採用。

### 實際交付介面

- `services/task_sync.py` 的 `ExpectedTaskVersion(task_uuid, generation, revision)` 是 immutable 預期版本；無現行資料為 generation/revision 均 None，不能把存在／不存在混用。
- `read_expected_task_version(session_factory, task_uuid)` 使用短 session 讀取版本後關閉；呼叫者接著在交易外讀 SE2，不占 row lock。新模組不 import／呼叫 reader，也不自行發網路請求。
- `task_sync_transaction(session_factory, expected, lock_timeout_ms=5000)` 擁有全新 session 與 transaction，以 READ COMMITTED 先取得 UUID advisory lock，再 SELECT FOR UPDATE 任務 row，核對 generation/revision 後 yield `LockedTask(session, expected, task)`。其他隔離層級先拒絕，避免鎖等待期間讀到固定舊 snapshot。
- 鎖鍵採 BLAKE2b digest_size8、固定 namespace `tsb-task-sync-v1`，轉 signed BIGINT；不同程序／PYTHONHASHSEED 相同。雜湊碰撞頂多導致額外串行化，不讓不同UUID誤當同一資料。
- `LockedTask.lock_details()` 在同 session 按明細 id 排序 FOR UPDATE，回完整明細，供 TSB-004 在取得鎖後複製已提交事件。鎖順序固定任務advisory → 任務row → 明細row。
- 正常退出先 flush；同 generation 的 revision 只由 guard 遞增一次（即使沒有欄位變更），呼叫者不可自行改 revision。新建／替換 generation 必須 revision0，新 generation ID 由後續核心產生。正常刪除現行任務可提交，不再寫 revision。
- 原始 task UUID 不可在 apply 重新命名；替換／搬移只能處理指定 UUID。caller 必須沿用 locked.session，不可內部 commit／rollback 或再用各自commit的DBController方法；外部通知與cache放 transaction 完成後。
- `TaskSyncConflict.retryable=True` 表示 prepared data 已過期、序列化／死鎖衝突等，需重新讀本地與遠端後再試；`TaskSyncLockTimeout` 是子型別，SQLSTATE55P03代表 advisory／row／details 等鎖等待逾時。預設5000ms，允許1～60000ms，transaction-local lock_timeout 不影響其他連線。不在此層自動重試，不把任意DB錯誤當成衝突。
- 取消／例外由 session.begin context rollback，等待中取消也測試釋放連線／鎖。TSB-004／005必須共用這個邊界；TSB-006／007還沒改接，舊 writer 不會遵守 advisory lock，本票不能單獨啟用正式搬移。
