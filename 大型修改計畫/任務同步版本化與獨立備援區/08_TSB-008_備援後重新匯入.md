## 目標與背景

既有程式可能已把遠端新建立時間寫入本地，導致受測者已重複、但新舊建立時間看起來相同。提供明確的人工作業意圖，先保留完整舊版，再從主系統重新匯入乾淨資料。

## 工作項目

1. 新增 `force_reload_sendtask` 工作類型，沿既有 JobManager／job item 模式受理，不在 HTTP request 內直接重建。
2. 依可信 org 檢查目前任務操作權限；多筆請求去重，未授權項目不進服務。只接受原始現行 UUID，不接受 `backup_id`。
3. 明確區分普通更新與強制重匯；工作意圖傳入 TSB-005，由核心在同一交易備援舊版、生成新 local generation、重匯資料。
4. 允許建立時間相同時重匯；備援原因用 `manual_reload`，不能以此宣稱主系統曾重建。
5. 完整資料準備前不得清空本地；遠端失敗保留現行，確認不存在則按既定規則移入備援，不偽稱重新匯入成功。
6. 重匯只從主系統資料重建現行 `second_*` 初始值；舊本地觸發保存在備援，不按 email／姓名移植到新明細。
7. 提供操作人、來源 UUID、舊／新本地版本、備援 ID、提交結果等紀錄，避免日後無法追蹤是人工修復還是遠端重建。

## 同 ID 事件語意

人工同版本重匯可能仍使用相同明細 UUID；本票不宣稱能從既有舊連結辨別人工重匯前後的世代。重匯後匹配現行明細 ID 的新事件依現行資料寫入，舊備援固定不追加。整個主系統重建時明細 UUID 會改變，與此情況不同。

## 驗收條件

- [x] 已有兩批重複明細、create_ut 相同的現行任務，修復後現行僅有完整遠端資料，舊明細完整留在備援。
- [x] 同 email 多模板多封信不被錯誤刪掉。
- [x] API 失敗／部分頁／交易中斷時，沒有先清空現行資料。
- [x] 同一工作重試不多造備援；刻意第二次人工重匯可建立另一個本地版本與備援。
- [x] org 授權、並發衝突、取消與部分成功均有明確結果。
- [x] 沒有自動全庫 reset，操作僅限使用者明確指定的任務。

## 聚焦驗證與交付

以主系統成功空資料、完整 N 筆與故障回應測試；用隔離資料庫驗證舊版快照完整。交付 job code、請求確認欄位／規則、結果與錯誤狀態給 TSB-009、012。

## 執行紀錄

### 實際變更與核心契約

- `TaskSyncService.prepare/sync` 增加可選的 `reload_intent=TaskReloadIntent(operation_id, actor, source_generation)`，只供可信服務內部建立。普通同步不傳此意圖，既有版本比較與 upsert 不變；不另寫一套替換演算法。
- 人工重匯在 prepare 前核對伺服器捕捉的來源 generation，完整讀取遠端並驗 org，交易內仍核對預期 generation／revision 與目前 org。排隊後已換世代回 `TaskSyncConflict`，不得順勢重匯新世代；準備期間同世代修訂改變，也拒絕過期結果。
- 完整成功時，無論 create_ut 是否相同，以 `manual_reload` 原子備援，再插入乾淨任務／明細與統計；新 generation、revision 0，不繼承舊 testcase 缺失欄位或 `second_*`，不依 email 去重或移植事件。沿既有欄位初始值，未觸發的 second 欄位是 NULL。人工意圖允許修復本地 create_ut 缺失的資料，但遠端版本仍須合法。
- 遠端失敗／部分頁／無效資料不寫入；明確 TaskNotFound 依既定規則回 `backed_up`、原因 `remote_missing`，不假稱重匯。人工成功狀態為 `reloaded`，與 `recreated` 分開；manual_reload 原因本身不宣稱遠端重建，歷史觀測仍僅依有效遠端建立時間差異判斷。
- `TaskSyncResult` 新增 `source_generation/source_revision/operation_id/actor/replayed`，既有欄位仍保留；新 generation／revision、backup_id 與 committed 由既有結果提供。所有寫入與操作紀錄提交成功後才回傳 committed=True。

### 操作紀錄與重試

- 新增 `repository/task_reload_schema.py`，在 `Base.metadata` 定義 `task_reload_operations`，主鍵 `(operation_id, task_uuid)`；保存可信 actor、操作當時 owner_gids、來源 generation、完整結果 JSONB、committed_at。獨立 migration 標記 `20261110_task_reload_operations_v1`，沿既有 init_db 接入，可重跑、交易失敗整體 rollback。
- 紀錄寫入與備援／重匯同一交易；不能用 JobRunItem 交易後的 completed 標記充當防重依據。同工作同 UUID 再執行時，驗 actor／source_generation／原操作 org 後回放結果、`replayed=True`，不再讀遠端、不再搬移或改目前任務。
- 同操作並發由既有每任務鎖串行化：過期版本衝突後，只有確實已有相同操作提交紀錄才回放，否則保持衝突。新工作 ID 且來源為新的現行 generation 才能刻意再重匯一次。
- 操作紀錄不以外鍵綁定現行／備援／JobRun，避免刪除備援或清理工作紀錄後失去防重依據；不含觸發陣列、受測者或密碼內容。即使備援已授權刪除，重試仍只回放歷史結果中的原 backup_id，不能據此重新建回已刪備援。回放的 generation／revision 是該次提交當時的版本，不保證仍為目前版本；下游必須依 changed_uuids 重新讀取現行資料。

### 請求與工作結果契約

入口為 `POST /api/jobs/start`：

```json
{
	"job_type": "force_reload_sendtask",
	"params": {
		"uuids": ["原始現行任務UUID"],
		"confirm_reload": true
	}
}
```

- `confirm_reload` 必須是 JSON 布林 true，不接受字串／數字；uuids 必須為非空字串陣列、每值不超過 36 字元，去重後只查現行 SendTask。拒絕 backup_id／backup_ids 參數；無清單不解讀為全部，無現行資料不改查備援。
- customer 一律拒絕；一般 user 用可信非空 org，admin_role=True 可全範圍。先篩除無權或不存在的現行項目，無任何可操作項目回 403，未授權 UUID 不進核心；工作執行與 apply 再驗 scope。前端傳 actor、org 或 source_generations 不採用。
- 沿 JobManager `items`／claim 模式去重與排隊，不在 HTTP request 讀明細或重建。operation_id 取實際 job_id，actor 取可信 username；`JobRun.request_params` 保存 `confirm_reload=True` 與伺服器捕捉的 source_generations，來源版本亦保存在工作閉包，供既有工作執行。
- `reload_job_items` 回 `reloaded_count/reloaded_tasks`、`reload_results`（含完整核心審計結果）、`backed_up_count/backed_up_tasks`、成功／失敗清單、changed_uuids、backups_changed、sync_statuses、notification_errors 與 job_status。backed_up 算同步已完成但 reloaded_count=0；一筆失敗不抹去其他提交，混合結果 partial、全失敗 failed。
- 工作項目回報失敗另記 notification_errors，不改稱 DB rollback；取消拋 `TaskSyncCancelled` 並帶 TaskSyncStatuses.results，核心已提交的操作紀錄仍可防重。JobManager／JobQueue 的完整取消結果持久化與 Redis 失效仍交給 009，不能以本票視為已完成。
