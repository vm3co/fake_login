## 目標

明確告訴前端哪些資料已提交、哪些被移入備援、哪些失敗，避免工作通知顯示成功卻沒刷新，或 Redis／通知故障把已完成交易誤稱失敗。

## 結果契約

沿既有 job result 相容擴充，定義並記錄實際欄位名稱：

| 類別 | 必備語意 |
| --- | --- |
| 每筆狀態 | 更新、重建、移入備援、封存／略過、失敗／衝突可明確區分 |
| 摘要 | `updated_count`、`backed_up_count`、`recreated_count` 及對應任務摘要；不得將移入備援顯示為永久刪除 |
| 資料失效 | 已提交的受影響現行 UUID、備援列表需刷新旗標，必要時要求整份清單重載 |
| 版本 | 現行新 generation／revision 供快取與前端來源識別，不作原始 UUID 替代值 |
| 部分結果 | 已提交項目與未完成／失敗項目分開；取消或工作最後失敗也保留已提交成果 |
| 告警 | DB 已提交但快取清除／通知失敗，以 warning 記錄，不宣稱已 rollback |

`backed_up` 是有效的資料變更，不是一般「未做事的跳過」。是否以 item completed 加 outcome，或增加明確狀態，需與既有 active item 唯一索引／終態判斷相容，並把選擇交付前端。

## 工作項目

1. 統一所有入口的摘要與 item outcome，不讓舊 `deleted` 分類繼續觸發錯誤文字或遺漏刷新。
2. 在每筆 commit 後累積／保存失效資訊；取消、partial、failed 仍能取得已提交 UUID。不能只在整個工作成功 return 時才保存。
3. 無 items 的清單工作也有可觀察的資料變更摘要；現有 job 列表序列化需可讀取新欄位，舊歷史工作有缺值時仍可顯示。
4. PostgreSQL commit 後使 `task:{uuid}:details` 失效，快取值加入 generation／revision envelope，讀取須核對目前現行版本。
5. 舊格式 cache／缺現行版本／generation 不一致當作 miss，不回傳上一代受測者；備援讀取禁止使用現行 cache key。
6. 防止舊讀取在替換後把舊值重新寫入而被當作新版使用；快取包裝必須帶取得資料當時的版本，不得事後套上新版本號。
7. 記錄 Redis 失效失敗並提供有限次重試或可觀察的後續清除，資料庫正確性不依賴 Redis 成功；通知在提交後發送。
8. 更新工作契約測試，不更換 JobQueue、不改排程啟用狀態。

## 驗收條件

- [x] 更新、重建、備援、封存、部分失敗各自有正確摘要，舊歷史工作仍可序列化。
- [x] 完成一筆後取消／下一筆失敗，第一筆失效資訊仍存在。
- [x] 無 items 的清單同步也能讓前端知道列表已改變。
- [x] Redis 留著舊資料或清除失敗時，不回傳舊世代明細。
- [x] 舊格式快取被視為 miss；備援與現行查詢完全隔離。
- [x] 通知送出失敗不抹掉 DB 成果，也不把已提交結果改稱回滾。

## 聚焦驗證與交付

測試固定的結果 JSON、部分提交後取消、模擬 Redis 失效失敗與舊快取重寫競態。交付狀態表、結果範例、失效事件來源與快取 envelope 格式，供 TSB-011、012 使用。

## 執行紀錄

### 實作與狀態契約

- `task_sync_entrypoints.summarize_task_sync` 統一輸出 `added/updated/recreated/reloaded/backed_up/unchanged/archived/unarchived/conflict/successful/failed` 的 `_count` 與 `_tasks`；封存轉換與主要同步結果可同時成立，不應把這些分類數量直接相加當總任務數。
- `sync_statuses` 保留 UUID → outcome 相容字典，`sync_results` 保存逐筆完整核心結果，包括 committed、generation／revision、backup_id、人工重匯審計與 replayed；不再只序列化 dict 而遺失附帶屬性。衝突仍為 error outcome，但 failed_tasks 的 `retryable=true` 與 conflict 分類可明確辨識。
- `changed_uuids` 為已提交的受影響現行來源；`backups_changed` 表示備援列表應刷新；`reload_list` 表示新增／重建／人工重匯／備援搬走／封存轉換需要重載清單。現行已搬走時，逐筆結果的 generation／revision 為 null，不以備援替代現行查詢。
- `warnings` 為物件陣列，含 task_uuid、stage、message，快取失效失敗另含 attempts。stage 使用 `cache_invalidation`、`progress`、`notification` 或相容 `post_commit`；notification_errors 仍保留相容欄位。只有告警時工作仍 completed，不能顯示資料庫 rollback。
- `target_tasks` 保存已選取的授權來源，`unfinished_tasks/unfinished_count` 區分尚未執行的目標；失敗與 skipped 不是尚未執行。清單工作在來源選定後保存目標，逐筆失敗／略過也保存；無 items 工作同樣適用。
- 工作整體終態保留 completed／partial／failed／cancelled。取消後即使已有提交，工作仍 cancelled，但提交結果與失效資訊可查；混合成功／失敗為 partial，全失敗為 failed。合併依每筆最新 outcome，不讓另一筆成功清除先前失敗，也不讓同 UUID 舊失敗壓過後續成功。
- item 沿既有狀態與 active 唯一索引：backed_up、recreated、reloaded 等提交結果標 completed，reason 保存 outcome；列表另提供 `outcome`。已提交 item 不被取消覆寫；終態保存會先完成已提交項目，再結束其他 pending／running 項目。未執行便取消的 queued 工作也會釋放 active items。
- 舊歷史 result 保留原欄位，缺新資訊時補 changed_uuids=[]、backups_changed=false、reload_list=false、warnings=[]；不捏造舊工作的提交版本。清單舊格式若沒有逐筆 results，保留原計數，不以空結果重算成零。

### 逐筆保存與取消

- 新增 `task_sync_progress.py`：以工作範圍 ContextVar 將提交結果送往既有佇列／預熱追蹤器。核心只在交易成功返回後進入 `_complete`，包括一般 apply、人工重匯與操作紀錄回放；外部通知、Redis 與工作回報不在資料交易內。
- `JobQueue.save_progress` 每筆提交後保存 JobRun.result，並同步完成有對應的已提交 item；JobManager 與 JobQueue 的終態合併已有結果，不以 None 或最後單筆回應覆蓋先前成果。啟動預熱的 tracked_scheduler_job 亦逐筆保存，不改排程開關或時刻、不更換 JobQueue。
- 核心提交後回報使用 shield；此時收到取消，先完成回報，再以 `TaskSyncCancelled` 附帶當筆成果向外傳遞。批次、清單及人工重匯上層會合併例外的當筆與前面成果，工作管理器保存後才結束未完成 items。
- JobRun 的進度保存是 PostgreSQL 核心提交後的獨立交易，不是跨資料表的交易式 outbox。程序被強制終止、主機故障或工作紀錄 DB 同時不可用時，不能宣稱此提交後窗口零遺失；保存失敗保留記憶體成果、回傳 progress warning 並寫日誌，終態仍可重試合併。008 的人工重匯防重紀錄仍與資料替換同交易，不受此限制影響。

### 明細快取契約

- 新增 `task_details_cache.py`，DBUser.get_sendlog 代理此服務，對外仍回明細陣列。Redis key 保持 `task:{uuid}:details`；快取一律保存含 id 的完整資料，need_id=False 只影響當次回傳投影，避免兩種呼叫共用 key 互相污染。
- envelope 格式為 `{"schema_version":1,"task_uuid":"task-1","generation":"local-generation","revision":3,"data":[...]}`。讀取必須先查 PostgreSQL 現行版本；舊陣列格式、壞 JSON、版本／類型不符、缺 id 或明細來源不符均 miss，任務不存在直接回 []。DB 版本查詢失敗不以 Redis 舊資料 fallback。
- 明細與 generation／revision 透過同一 SQL statement 的任務／明細 outer join 取得一致快照，不事後將舊明細套上新版本。快取命中後、資料讀取後與快取回寫後均核對現行版本；最多三輪，持續切換時拋 TaskSyncConflict，不回已知過期明細。
- 舊讀取即使在新世代替換與失效之後才寫回，也只能帶舊 envelope，後續請求會拒絕；同步與人工重匯不依賴 Redis 清除成功來維持世代正確性。此驗證以查詢時的版本為準，不宣稱在 HTTP 返回後資料永不變更。
- 有效零筆明細也可快取；TTL 沿用未封存 86400 秒、已封存 3600 秒。use_cache=False 不讀 Redis，但仍可以當次一致快照更新快取。
- 每次核心已提交、changed_uuids 非空時刪除 key；包括人工重匯 replay。每次刪除最多兩次，每次上限 0.5 秒；都失敗留下 attempts=2 的 warning。讀寫快取各自上限 0.5 秒，故障回 DB，不將 Redis 成功當 PostgreSQL 正確性條件。
- 備援查閱不得呼叫此現行快取或回退到它；備援 API 仍由 010 實作。triggerapp 事件與封存 worker 目前只刪相同 key，未改成寫 envelope、不重構事件流程；同世代事件的既有失效機制維持，不新增事件世代演算法。
