## 目標

安全啟用版本同步與備援區，先用一筆已知重複任務做修復試點，再依明確選取逐步處理其他任務。不得讓舊同步程式在切換期間繼續永久刪除或覆寫版本。

## 備份現況與限制

- 截至本次調查，Compose 僅掛 `./pg_backup:/backup`，該資料夾為空；未查到專案內或可讀系統排程的資料庫定時備份。
- 私人 crontab 無權讀取，不能完全排除外部備份；結論是尚無已驗證的自動備份，不是保證世界上沒有其他備份。
- PostgreSQL named volume／Redis AOF 是資料持久化，不是已驗證的獨立資料庫備份。
- 備援表仍在同一 PostgreSQL，不能保證磁碟／資料庫災難復原。
- 本票不新增 cron、backup container、每日保留政策或異機同步；一次人工完整備份與還原演練是這次切換門檻。

## 執行順序

1. 在維護窗口停止舊資料寫入，確認寫入邊界與 queue 狀態。
2. 執行一次完整 PostgreSQL `pg_dump -Fc`，記錄時間、檔名、檔案大小及校驗值；連線憑證透過操作者／環境提供，不放進文件或輸出。
3. 列出 dump 內容，並在獨立臨時資料庫實際 restore，核對關鍵表、任務／明細筆數與原始事件陣列。僅看到檔案存在不算還原驗證。
4. 套用 TSB-002 migration，核對版本補值、constraint 與重跑冪等，確認舊資料尚未被搬移。
5. 部署全部已驗收的後端與前端版本，確保所有同步入口都走新核心、備援 API／UI 已可用；清理或依版本機制使舊 Redis cache 失效。
6. 選一個明確指定的已知重複任務，取得使用者確認，執行「備援後重新匯入」。核對舊資料完整留在備援，現行筆數／受測者／樣板與主系統一致，沒有 email 去重副作用。
7. 以同 org 使用者驗證備援查閱、本地匯出、重建標記；選測試備援驗證刪除只影響該版本，不以刪除正式歷史資料作預設測試。
8. 恢復 worker 與原有排程／warming 設定，逐步監測重建、備援、error／partial、鎖衝突及 Redis warning；不要自動重匯全庫。
9. 其他任務修復以明確選取分批執行，保存操作與備援 ID 紀錄；不自動刪舊備援。

## 回復程序與禁止事項

1. 異常時先停止同步／事件寫入，保存目前版本與錯誤證據，確認已有哪些備援搬移提交。
2. 不能直接切回不認識備援表的舊程式：舊程式看不到已搬資料，還可能繼續永久刪除／混寫。
3. 優先評估停用新功能並保持資料可查；若需完整回復，以已驗證 dump 在確認目標後還原，不能在未知正式目標試指令。
4. 還原會退回備份時間點，需先說明維護後新寫入／事件的取捨並取得操作者確認；資料表與 Redis／事件 queue 的時間點要一致處理，避免重播到錯誤版本。
5. 回復後重新核對關鍵資料與原排程設定，再恢復服務。不得用 `docker compose down -v` 或刪 named volume 當作一般修復步驟。
